- добавлена AI-генерация контент-плана;

До этого разрешены:

- критические исправления;
- устранение угроз безопасности;

- передача в существующий AI-бриф данных, необходимых для интеграции готовых разделов.

Новые самостоятельные AI-функции до этапа 4 не добавляются.

**Приоритет:** Высокий  
**Статус:** Следующая задача

### Цель

Позволить использовать сохранённые идеи постов как дополнительный контекст при создании контент-плана.

Пользователь не должен вручную копировать уже сохранённые идеи в новый бриф.

### Планируемые задачи

- загрузить идеи из `post_ideas.txt`;
- определить удобный способ выбора идей;

- не ломать создание плана без сохранённых идей;
- сохранить текущую структуру AI-запроса;
- не добавлять новые AI-режимы и отдельные промпты;
- добавить переходы «⬅️ Назад»;
- обработать пустой список идей;
- обработать неправильный выбор;

## Полная проверка интеграции четырёх разделов

**Приоритет:** Высокий  
**Статус:** Не начато

### Проверяемый сценарий

1. Создать клиента.
2. Создать несколько идей постов.
3. Создать пост для выбранного клиента на основе сохранённой идеи.
4. Создать контент-план для того же клиента.
5. Передать в контент-план сохранённые идеи.
6. Найти созданный пост.
7. Найти контент-план по имени клиента или теме.
8. Отредактировать записи.
9. Удалить тестовые записи.
10. Проверить переходы «⬅️ Назад».

### Дополнительные проверки

- пустой список клиентов;
- пустой список идей;
- неправильный выбор;
- одинаковые имена клиентов;
- длинные списки;
- старые записи в файлах;
- длинные сообщения Telegram;
- ошибки OpenAI;
- отсутствие сохранения неполного AI-результата.

# Абстракция AI-провайдера

**Приоритет:** Средний  
**Статус:** Отложено до этапа 4 «Искусственный интеллект» и стабилизации первой версии

### Цель

Подготовить SMM Bot к работе с несколькими AI-провайдерами через единый внутренний интерфейс.

Это позволит менять модель или сервис без переписывания основной логики разделов, использующих искусственный интеллект.

### Возможности

- выбирать AI-провайдера в зависимости от цены, скорости и качества;
- использовать OpenAI и другие сервисы с OpenAI-совместимым API;
- уменьшить зависимость проекта от одного поставщика;
- упростить переход на более выгодную или качественную модель;
- сохранить одинаковую логику вызова AI для разных разделов проекта.

### Планируемые задачи

- определить единый интерфейс для обращения к AI;
- вынести работу с конкретным провайдером из Telegram handlers;
- создать реализации только для реально необходимых провайдеров;
- хранить выбор провайдера и модели в настройках;
- использовать безопасные переменные окружения для API-ключей;
- добавить обработку различий между API провайдеров;
- предусмотреть понятные сообщения об ошибках;
- добавить тесты переключения между провайдерами;
- задокументировать ограничения каждого поддерживаемого сервиса.

### Ограничения

- не реализовывать во время этапа 2;
- не переносить весь архитектурный этап вперёд ради одной функции;
- до этапа 4 не добавлять новые AI-провайдеры;
- не создавать универсальную AI-платформу без подтверждённой необходимости;
- сначала стабилизировать существующую AI-функцию;
- не считать OpenAI-совместимый API гарантией полной совместимости сервисов.

### Условие начала реализации

Приступать только после:

- завершения этапа 2 «Интеграция разделов»;
- выполнения необходимых архитектурных задач этапа 3;
- начала планового этапа 4;
- стабилизации первой рабочей версии SMM Bot;
- появления практической необходимости использовать больше одного AI-провайдера.

### Ожидаемый результат

Разделы SMM Bot используют единый внутренний интерфейс для работы с искусственным интеллектом.

Конкретный AI-провайдер можно заменить через настройки без значительного изменения бизнес-логики проекта.

# Правило использования Codex

Codex используется для конкретных задач, требующих работы непосредственно с репозиторием:

- изучения нескольких файлов;
- реализации согласованных изменений;
- поиска ошибок;
- ограниченного рефакторинга;
- запуска тестов;
- проверки безопасности;
- ревью изменений перед коммитом.

Codex не используется без необходимости для:

- обычных разговоров;
- простых теоретических вопросов;
- задач, которые пользователь выполняет самостоятельно ради обучения.

Каждая задача для Codex должна иметь:

- понятную цель;
- ограниченный объём;
- проверяемый результат.

Перед коммитом обязательно проверяются изменения и доступные тесты.

Codex не должен:

- принимать крупные архитектурные решения молча;
- расширять объём задачи без необходимости;
- перепрыгивать на следующий этап ROADMAP;
- лишать проект учебной ценности.

Основные инструкции для работы Codex непосредственно с репозиторием должны храниться в корневом `AGENTS.md`.

Создание и заполнение `AGENTS.md` остаётся отдельной технической задачей.

# Правило ведения code_history

Перед крупным изменением предыдущая рабочая версия сохраняется в `code_history`.

Каждая сохранённая версия должна содержать:

1. что нового относительно предыдущей версии;
2. что версия умеет;
3. текущие ограничения;
4. почему версия сохранена.

Во время основной разработки создаётся финальная рабочая версия раздела.

Промежуточные версии:

- заранее планируются в CHANGELOG;
- могут иметь подготовленные пустые файлы;
- не обязаны реализовываться во время основной разработки;
- восстанавливаются позже во время отдельного обучения.

`code_history` используется как учебная история развития кода.

Git используется как фактическая история изменений проекта.

# Правило проверки нового кода

После каждого нового или существенно обновлённого кода София должна предоставить конкретный список ручных проверок.

Список должен включать:

- основной сценарий;
- альтернативные варианты;
- пустые данные;
- неправильный ввод;
- переходы «⬅️ Назад»;
- сохранение;
- просмотр;
- поиск;
- редактирование;
- удаление, если оно предусмотрено.

Только после успешной проверки:

- версия сохраняется в `code_history`;
- обновляется разделовый CHANGELOG;
- создаётся отдельный Git-коммит;
- коммит отправляется на GitHub.

# Общее правило проекта

До завершения основной функциональности и текущего этапа ROADMAP не выполнять крупные архитектурные рефакторинги, направленные исключительно на повторное использование кода.

Все такие идеи фиксируются в BACKLOG и реализуются после выпуска и стабилизации первой версии SMM Bot.

Каждая новая функция оценивается по критерию:

> Делает ли она работу пользователя проще, быстрее, безопаснее или качественнее?

Если идея не помогает текущему этапу или не решает реальную проблему пользователя, она остаётся в BACKLOG и не внедряется преждевременно.

# Активные задачи

## Архитектура v2.5

Статус: 🟡 В процессе

Приоритет: Высокий


Цель:

Создать устойчивую структуру проекта:

handlers
    ↓
services
    ↓
storage
services ← models
storage  ← models


Ответственность:

### handlers

Только:

- Telegram;
- сообщения;
- клавиатуры;
- FSM;
- пользовательские сценарии.

### services

Только:

- бизнес-логика;
- правила работы данных;
- проверки;
- операции над сущностями.

### storage

Только:

- чтение данных;
- сохранение данных;
- преобразование форматов.

### models

Только:

- структуры данных;
- модели объектов.


Принцип:

Не вводить Repository Pattern, Dependency Injection, factories, interfaces, adapters и другие дополнительные архитектурные уровни без реальной необходимости.

Архитектура должна оставаться достаточно простой для текущего размера проекта.

# Обнаруженные проблемы и технический долг

## FSM — кнопки меню воспринимаются как пользовательский ввод

Статус: 🐞 Зафиксировано

Приоритет: Средний


Проблема:

Когда бот находится в FSM-состоянии и ожидает свободный текст, обычная клавиатура раздела остаётся доступной.

Например:

1. пользователь нажимает «➕ Добавить идею»;
2. бот ожидает текст новой идеи;
3. пользователь нажимает кнопку «🔍 Найти идею»;
4. текст кнопки может быть воспринят как новая идея и сохранён.

Задача:

- определить единое UX-решение для FSM-сценариев;
- во время ожидания свободного ввода:
  - либо скрывать обычную клавиатуру;
  - либо показывать отдельную кнопку «Отмена»;
  - либо явно обрабатывать кнопки меню и не принимать их как данные.

Проверить проблему не только в «Идеях постов», но и в других FSM-сценариях.

Не исправлять во время архитектурного этапа, если проблема не мешает текущей работе.

---

## Добавление идеи в UTF-8 файл без завершающего переноса строки

Статус: 🐞 Зафиксировано

Приоритет: Низкий


Проблема:

Текущая логика append в `post_ideas.txt` проверяет последний символ через перемещение файлового указателя.

При UTF-8 тексте без завершающего `\n` последний символ может занимать несколько байтов, что потенциально может привести к ошибке декодирования.

Задача:

- заменить проверку последнего символа на безопасный вариант;
- сохранить совместимость с существующим файлом;
- добавить отдельный тест.

Исправить после текущего архитектурного шага либо во время технической очистки.

# Продуктовые принципы

## Минимум независимых функций — максимум связности

Новая возможность не должна автоматически становиться новым пунктом меню.

Сначала необходимо проверить:

- можно ли встроить её в существующий сценарий;
- можно ли использовать уже существующие данные;
- усиливает ли она другие функции продукта.

Отдельный раздел создавать только для самостоятельной регулярно используемой задачи.

---

## Одна информация — несколько преимуществ

Данные не должны использоваться только один раз.

Например:

Brand Voice клиента может использоваться:

- при генерации идей;
- при создании поста;
- при контент-планировании;
- при рерайте;
- при адаптации под площадки;
- при AI-рекомендациях.

Чем больше функций продукта разумно используют одни и те же данные, тем сильнее экосистема.

---

## Функции должны усиливать друг друга

Предпочтение отдаётся функциям, которые становятся полезнее благодаря существующим возможностям проекта.

Изолированная функция требует отдельного сильного обоснования.

---

## AI — часть продукта, а не отдельный аттракцион

AI по возможности должен работать внутри обычных пользовательских сценариев.

Не создавать отдельные AI-разделы только ради демонстрации AI.

Пользователь должен получать полезный результат, а не думать о том, какой технический механизм использован внутри.

---

## Не копировать конкурентов автоматически

Наличие функции у крупного конкурента не является достаточной причиной для её добавления.

Перед добавлением необходимо проверить:

- экономит ли она время SMM-специалиста;
- улучшает ли качество работы;
- убирает ли реальную рутину;
- усиливает ли существующую экосистему.

---

## Сначала ROADMAP — затем расширение

Текущий ROADMAP остаётся основой разработки.

Новые крупные функции не должны отвлекать от завершения запланированных этапов.

После завершения ROADMAP проект можно развивать как долгосрочную платформу без жёсткого ограничения первоначальным набором функций.

---

## Сначала работающий продукт

Порядок приоритетов:

1. завершить текущую архитектуру;
2. завершить ROADMAP;
3. получить стабильную версию;
4. разместить бота на сервере;
5. получить первых реальных пользователей;
6. собрать обратную связь;
7. развивать продукт на основании реальных потребностей.

Не начинать преждевременно:

- мобильное приложение;
- сложную коммерческую инфраструктуру;
- избыточную универсализацию;
- крупные архитектурные переделки ради будущих гипотетических задач.

# Правила BACKLOG

BACKLOG используется для:

- сохранения будущих идей;
- фиксации технического долга;
- планирования следующих этапов;
- сохранения продуктовых гипотез;
- сохранения идей, которые нельзя внедрять прямо сейчас.


Не используется для:

- срочного добавления новых функций;
- расширения текущего этапа без оценки;
- преждевременной универсализации;
- автоматического копирования функций конкурентов.


Каждая новая задача оценивается:

- делает ли она продукт лучше;
- экономит ли она время SMM-специалиста;
- улучшает ли качество его работы;
- убирает ли рутинное действие;
- нужна ли она текущему этапу;
- можно ли встроить её в существующий сценарий;
- использует ли она уже существующие данные;
- усиливает ли она другие функции;
- не создаёт ли лишний технический долг.


Если новая задача:

- не добавляет пользовательскую возможность;
- а только улучшает код, архитектуру, тестирование, надёжность или внутреннюю структуру;

она относится к техническим задачам BACKLOG, а не смешивается с функциональной разработкой.


Крупные архитектурные рефакторинги ради переиспользования откладываются до завершения основной функциональности.

После выпуска первой стабильной версии необходимо провести отдельный технический maintenance-pass:

- проверить зависимости;
- оценить обновления библиотек и фреймворков;
- проверить документацию;
- проверить архитектуру;
- проверить тесты;
- проверить общее техническое состояние проекта.

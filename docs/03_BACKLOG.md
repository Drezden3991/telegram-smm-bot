# Завершённый этап 3 — Архитектура v2.5

Статус: ✅ Завершено

Архитектура проекта:

handlers
    ↓
services
    ↓
storage

services ← models
storage  ← models


Ответственность:

### handlers

Только:

- Telegram;
- сообщения;
- клавиатуры;
- FSM;
- пользовательские сценарии.

### services

Только:

- бизнес-логика;
- правила работы данных;
- проверки;
- операции над сущностями;
- подготовка данных для AI;
- orchestration AI-сценариев.

### storage

Только:

- чтение данных;
- сохранение данных;
- parsing;
- serialization;
- преобразование файловых форматов.

### models

Только:

- структуры данных;
- модели объектов;
- схемы структурированных AI-ответов.


Главный архитектурный принцип:

Не вводить Repository Pattern, Dependency Injection, factories, interfaces, adapters, универсальный AIProvider и дополнительные архитектурные уровни без реальной необходимости.

Архитектура должна оставаться достаточно простой для текущего размера проекта.

## Groq

Статус: ✅ Provider/service-слой реализован

Модель:

`openai/gpt-oss-120b`

Reasoning:

`low`

Реализованы направления:

- Content Plan;
- Write Post;
- Post Ideas.

Преимущество, замеченное в smoke-тестах:

- высокая скорость ответа.

Обнаружено:

Groq Structured Outputs требует:

`additionalProperties: false`

для объектов JSON Schema.

Для совместимости Pydantic-моделей добавлено:

`ConfigDict(extra="forbid")`

в:

- `ContentPlanDay`;
- `SevenDayContentPlan`;
- `GeneratedPostIdeas`.

Также наблюдались случаи, когда Groq генерировал содержимое, не проходящее ограничения собственной JSON Schema.

Не строить критическую бизнес-логику на предположении, что Structured Output гарантирует корректность содержания.

# Сравнение AI-провайдеров

Статус: ✅ Базовая инфраструктура подготовлена

Создан developer-only инструмент:

`scripts/compare_ai_providers.py`

Назначение:

сравнивать несколько провайдеров на одинаковых исходных данных.

Поддерживаемые режимы:

- `content_plan`;
- `write_post`;
- `post_ideas`.

Инструмент:

- не используется Telegram-пользователем;
- не сохраняет данные;
- не выбирает победителя автоматически;
- показывает результат каждого провайдера;
- показывает время выполнения;
- изолирует ошибки одного провайдера от других.

Проведены первые реальные smoke-сравнения.

Наблюдения:

- все проверенные генеративные модели способны выдавать полезный результат;
- все могут придумывать неподтверждённые бизнес-факты;
- OpenAI в первом сравнении Content Plan оказался аккуратнее в работе с подтверждёнными фактами;
- Gemini и Groq также требуют человеческой проверки;
- Groq показал высокую скорость ответа.

Решение:

не продолжать длительное ручное сравнение моделей на искусственных примерах.

Основную продуктовую оценку проводить на реальной работе заказчицы.

# Обнаруженные проблемы и технический долг

## FSM — кнопки меню воспринимаются как пользовательский ввод

Статус: 🐞 Зафиксировано

Приоритет: Средний


Проблема:

Когда бот находится в FSM-состоянии и ожидает свободный текст, обычная клавиатура раздела остаётся доступной.

Например:

1. пользователь нажимает «➕ Добавить идею»;
2. бот ожидает текст;
3. пользователь нажимает «🔍 Найти идею»;
4. текст кнопки может быть воспринят как пользовательские данные.

Задача:

выбрать единый UX-подход:

- скрывать обычную клавиатуру;
- показывать кнопку отмены;
- либо явно перехватывать кнопки меню.

Проверить проблему во всех FSM-сценариях.

# Правила BACKLOG

BACKLOG используется для:

- будущих идей;
- технического долга;
- продуктовых гипотез;
- известных некритических ошибок;
- отложенных функций;
- идей, которые нельзя внедрять сейчас.

Не используется для:

- внезапного расширения текущего scope;
- преждевременной универсализации;
- архитектуры ради архитектуры;
- автоматического копирования конкурентов.

Каждая новая задача оценивается:

- делает ли она продукт лучше;
- экономит ли время SMM-специалиста;
- улучшает ли качество;
- убирает ли рутину;
- нужна ли она текущему этапу;
- можно ли встроить её в существующий сценарий;
- использует ли она существующие данные;
- усиливает ли она другие функции;
- создаёт ли лишний технический долг.

Если задача не добавляет пользовательскую функцию, а улучшает:

- код;
- архитектуру;
- тестирование;
- надёжность;
- developer experience;

она относится к техническому BACKLOG.

Крупные архитектурные рефакторинги ради переиспользования откладываются до завершения основной функциональности.

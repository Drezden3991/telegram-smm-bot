# SMM Bot — Project Roadmap

Дата создания: 03.07.2026  
Последнее обновление: 19.07.2026

---

# Цель проекта

Создать коммерческий Telegram-бот для помощи SMM-специалистам: вести клиентов, хранить идеи, готовить посты и создавать контент-планы.

Проект развивается небольшими законченными версиями. Базовый MVP завершён; текущий активный этап — точечное внедрение OpenAI API без крупного архитектурного рефакторинга.

---

# Текущее состояние

- ✅ Базовый MVP всех четырёх разделов завершён.
- 🟨 Интеграция данных между разделами реализована частично.
- ⬜ Архитектурное улучшение не начато.
- 🟨 Этап искусственного интеллекта начат.
- ⬜ Коммерческий релиз и деплой не начаты.

Текущая новая версия:

- 📅 Контент-план — v1.1, AI-генератор на семь дней.

# Этап 1 — Базовый MVP

Статус: ✅ Завершён

## 👥 Клиенты — v1.0

Реализованы добавление, просмотр, карточка, поиск, редактирование, удаление и проверка дубликатов. Данные хранятся в `clients.txt`.

## 💡 Идеи постов — v1.0

Реализованы случайная идея, добавление, просмотр, поиск, редактирование, удаление и проверка дубликатов. Данные хранятся в `post_ideas.txt`.

## ✍️ Написать пост — v1.0

Реализованы выбор клиента, выбор темы/идеи, выбор стиля, шаблонное создание поста, история, поиск и удаление. Данные постов сохраняются в JSON-файл `posts.txt`.

## 📅 Контент-план — v1.0

Реализованы создание статического плана по теме, сохранение, просмотр, поиск, редактирование и удаление. Сценарии используют aiogram FSM, данные хранятся в `content_plans.txt`.

# Этап 2 — Интеграция разделов

Статус: 🟨 Частично реализовано

Уже есть:

- раздел «Написать пост» читает список клиентов;
- раздел «Написать пост» показывает сохранённые идеи;
- основные роутеры объединены в одном Telegram-боте.

Остаётся:

- перейти от текстового ввода клиента к устойчивому выбору записи;
- связать контент-планы с клиентами и сохранёнными идеями;
- определить структурированные идентификаторы данных;
- исключить неоднозначность при одинаковых именах и текстах.

# Этап 4 — Искусственный интеллект

Статус: 🟨 В процессе

## 📅 Контент-план v1.1 — реализовано

- OpenAI Responses API.
- Модель `gpt-5.6`.
- `reasoning.effort="low"`.
- Structured Outputs через Pydantic.
- Ровно семь дней в порядке от 1 до 7.
- Для каждого дня: цель, тема, формат, ключевой тезис и CTA.
- Один пользовательский бриф до 500 символов.
- Асинхронное ожидание API без блокировки цикла aiogram.
- Создание и редактирование используют один AI-контракт.
- При ошибке API или неверной структуре ничего не сохраняется.
- Понятные сообщения для ошибок авторизации, лимита, сети, тайм-аута и сервиса.
- Сохранены просмотр, поиск, редактирование и удаление контент-планов.

## Проверка v1.1

Завершено без обращения к OpenAI API:

- компиляция активного и архивного обработчика;
- проверка сигнатуры установленного OpenAI SDK;
- тест модели, reasoning и Structured Outputs;
- тест семидневной структуры и Telegram-форматирования;
- тест отказа от сохранения при ошибке API;
- проверка совместимости установленных зависимостей.

Остаётся отдельный live smoke test с одним реальным запросом после явного подтверждения пользователя.

# Текущие ограничения

- Файловое хранение не рассчитано на конкурентную работу большого числа пользователей.
- Нет базы данных, миграций и пользовательской изоляции.
- Нет полноценного автоматизированного тестового набора для остальных разделов.
- AI-контент-план ещё не подтверждён реальным API-запросом.
- Разделы «Идеи постов» и «Написать пост» пока используют шаблонную, не AI-генерацию.
- Деплой и production-настройки отсутствуют.

---

# Ближайшие шаги

1. После отдельного подтверждения выполнить один live smoke test AI-контент-плана.
2. При успешном результате зафиксировать live-проверку в документации.
3. Проверить UX на реальном Telegram-сообщении и длину ответа.
4. Выбрать следующую одну AI-функцию без расширения архитектурного контура.
5. Отдельно запланировать переход к структурированному хранилищу.

---

# Принцип развития

Каждая версия должна быть законченной, проверяемой и ограниченной по области изменений.

Новые AI-функции добавляются по одной, не должны ломать существующие CRUD-сценарии и не должны сохранять неполный результат.

# PROJECT ROADMAP — SMM Bot / SMM Platform

Дата обновления: 22.08.2026

---

# 1. Общая цель проекта

Создать связанный рабочий инструмент для SMM-специалиста, который помогает пройти весь цикл работы с контентом:

Клиент
→ контекст и Brand Voice
→ идеи
→ контент-план
→ готовый пост
→ редактирование
→ адаптация
→ согласование
→ планирование
→ публикация
→ метрики
→ анализ
→ следующий контент-план

Проект начинался как Telegram-бот, но долгосрочно должен развиваться в единую SMM-платформу.

Telegram не рассматривается как временный прототип, который потом выбрасывается.

Целевая архитектура в будущем:

Telegram Bot
        ↓
   Backend / API
        ↑
     Web App
        ↑
   PWA / Mobile later

Telegram должен остаться дополнительным быстрым интерфейсом для:

- уведомлений;
- быстрых AI-запросов;
- согласований;
- статусов;
- оперативных действий.

Web должен стать основным интерфейсом для сложной визуальной работы:

- календарь;
- большие списки контента;
- media library;
- аналитика;
- отчёты;
- inbox;
- команды;
- публикация;
- управление несколькими клиентами.

# 2. Основные принципы разработки

## Сначала работающий продукт

Не строить инфраструктуру ради будущего, пока нет реальной задачи.

Порядок:

1. рабочая функция;
2. тесты;
3. реальное использование;
4. обратная связь;
5. только затем усложнение.

---

## Минимум независимых функций — максимум связности

Новая возможность не должна автоматически становиться новым пунктом меню.

Сначала проверить:

- можно ли встроить её в существующий сценарий;
- использует ли она уже существующие данные;
- усиливает ли она другие функции.

Пример:

Brand Voice должен работать сразу в:

- Post Ideas;
- Write Post;
- Content Plan;
- AI Editor;
- Platform Adaptation.

---

## AI — часть продукта, а не отдельный аттракцион

Пользователю важен результат, а не API или название модели.

AI должен работать внутри обычных сценариев.

---

## AI не является гарантированным источником фактов

Structured Output и Pydantic проверяют структуру, но не истинность содержания.

AI-результаты считаются черновиками.

Человек остаётся ответственным за проверку результата перед публикацией.

---

## Сначала текущий ROADMAP — потом новые крупные идеи

Новые хорошие идеи фиксируются в BACKLOG.

Они не должны автоматически вмешиваться в текущий этап.

---

## Не усложнять архитектуру без реальной причины

Не вводить заранее:

- Repository Pattern;
- Dependency Injection;
- factories;
- interfaces;
- adapters;
- универсальный AIProvider;
- дополнительные архитектурные уровни.

Возвращаться к ним только если существующая архитектура реально начинает мешать.

---

# 3. Текущая архитектура

Используется архитектура v2.5:

handlers
    ↓
services
    ↓
storage

services ← models
storage  ← models

## handlers

Отвечают за:

- Telegram;
- сообщения;
- клавиатуры;
- FSM;
- пользовательские сценарии.

## services

Отвечают за:

- бизнес-логику;
- проверки;
- операции над сущностями;
- подготовку AI-контекста;
- orchestration AI-сценариев.

## storage

Отвечает за:

- SQLite;
- чтение;
- запись;
- миграции;
- преобразование хранимых данных.

## models

Отвечает за:

- модели сущностей;
- структуры данных;
- Pydantic-схемы AI-ответов.

# 11. Этап 8 — Content Plan → готовый Post

Статус: ⬜ Запланировано

Цель:

Связать уже существующие Content Plan и Write Post в единый workflow.

## Проблема до Stage 8

Пользователь создаёт:

`Content Plan`

Затем видит хороший пункт плана.

Но чтобы получить готовый пост, ему приходится:

- переходить в Write Post;
- снова выбирать клиента;
- снова вводить тему;
- снова передавать контекст.

Это лишняя работа.

## Новый workflow

Контент-план
→ выбрать день
→ `✍️ Создать пост`

Система автоматически знает:

- клиента;
- Brand Voice;
- день плана;
- цель;
- topic;
- format;
- key message;
- CTA.

Пользователь выбирает:

- шаблон;
- OpenAI;
- Gemini;
- Groq.

Затем получает обычный Post.

## Важно

Не создавать второй отдельный механизм генерации постов.

Stage 8 должен использовать существующий:

`Write Post service`

Content Plan только передаёт ему готовый контекст.

### Definition of Done

- из сохранённого Content Plan можно выбрать день;
- можно создать Post;
- не требуется повторный ввод клиентских данных;
- Brand Voice используется автоматически;
- новый Post сохраняется обычным способом;
- сохраняется multi-user isolation;
- старый Write Post продолжает работать независимо;
- тесты проходят.

### Откуда пришли

Stage 7 дал устойчивый Brand Voice.

Stage 8 использует его вместе с уже существующим Content Plan.

### Куда идём дальше

После генерации связанного поста появляется естественная потребность быстро изменять уже готовый текст.

Следующий этап — AI Editor.

# 17. Этап 14 — Audio → Content

Статус: ⬜ Запланировано

`stage-7-brand-voice`

1. оценить bug;

Не смешивать незавершённый Stage 7 с версией, которую тестирует заказчица.

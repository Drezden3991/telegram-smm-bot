# Подготовка этапа 3 — Архитектура v2.5

После завершения этапа 2 проведён анализ структуры проекта.

Выявлены проблемы:

- Telegram handlers содержат слишком много логики;
- работа с файлами находится внутри handlers;
- есть дублирование чтения данных;
- бизнес-логика смешана с интерфейсом;
- модели данных находятся рядом с Telegram-кодом.

---

# Выбранное архитектурное решение

Используется архитектура v2.5:

handlers
    ↓
services
    ↓
storage
models


Цель:

Разделить ответственность компонентов.

---

## handlers

Отвечают за:

- Telegram;
- сообщения;
- клавиатуры;
- FSM;
- пользовательские сценарии.

---

## services

Отвечают за:

- бизнес-логику;
- правила работы данных;
- операции над объектами.

Не зависят от aiogram.

---

## storage

Отвечает за:

- чтение данных;
- сохранение данных;
- преобразование форматов.

Не содержит бизнес-правил.

---

## models

Отвечает за:

- структуры данных;
- модели объектов.

---

# Правила внедрения v2.5

Архитектурные изменения выполняются небольшими шагами.

- `git diff --check`;
- ручная проверка затронутого раздела;
- Git-коммит после успешной проверки.
